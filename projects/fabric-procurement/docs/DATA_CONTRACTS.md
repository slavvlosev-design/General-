# Контракты данных

Версия 1.0. Проектное описание нормализованных структур, а не существующий API. Все идентификаторы — строки, количества — десятичные числа, даты — ISO 8601. Пустое поле не означает ноль.

## Общие поля происхождения

Каждая запись содержит `source_id`, SHA-256 исходника, имя листа, номер строки, время импорта и версию схемы. Нормализованные значения хранятся рядом с исходными. Техническая нормализация не уничтожает исходное написание.

## 1. План продаж `sales_plan`

Обязательные поля: `plan_version`, `cabinet`, `product_id_source`, `period_start`, `period_end_exclusive`, `sales_qty`, `qty_unit=piece`. Дополнительные: ткань из плана, категория, менеджер (не требуется расчётному ядру).

Адаптер текущего файла: «ПЛАН 2027», заголовок в строке 4; B — артикул, F — ткань, H — кабинет, W:AH — «Продажи (шт)». Строки 1–3 — заголовки/итоги, не изделия. Сначала проверять заголовки, потом позицию: сдвиг столбцов должен обнаруживаться. Кабинет — точное значение «ООО Фабрика» после удаления внешних пробелов. Не включать «ООО АКА» и «АКА».

Один факт спроса: версия плана + кабинет + изделие + период + явно заданные дополнительные измерения. Повторы этого ключа блокируют автоматическое суммирование до выяснения. Нулевые значения допустимы, пустые и ошибки Excel — нет. Отрицательные продажи требуют отдельного правила возвратов; по умолчанию ошибка. Проверять все 12 месяцев и год плана.

## 2. Связи артикулов `product_mapping`

Поля: исходная система, артикул плана, `product_id_1c`, `status` (proposed/confirmed/rejected), основание, подтвердивший, дата и срок действия.

Точное совпадение в выгрузке — проверяемая связь. Преобразование старого формата — кандидат. Одна исходная позиция не должна вести к нескольким изделиям без явного правила разделения. Изменение связи создаёт версию, не переписывает историю.

## 3. Спецификации `bom_component`

Поля: `product_id_1c`, `spec_id`, `spec_version`, срок действия, `output_qty`, единица выпуска, `component_line_id`, `material_id_1c`, имя материала, категория, характеристика, `component_qty`, единица, размер изделия (если применимо).

Норма на изделие = количество материала / количество выпуска после преобразования единиц. Норма должна быть положительной. Явная нулевая норма требует объяснения, а не молчаливого принятия.

Текущий XLS: A спецификация, B номенклатура, C характеристика изделия, D материал, E характеристика материала, F количество. Код материала, единицы, база выпуска, действующая версия и идентификатор строки отсутствуют как отдельные поля. Их отсутствие — известное ограничение выгрузки.

Равные строки не гарантируют дубль: нужны версия и идентификатор компонента. Разные компоненты одной ткани суммируются только после подтверждения смысла. Несколько действующих спецификаций одного изделия — конфликт, не усреднение.

## 4. Материалы `material_master`

Поля: `material_id_1c`, полное название, вид ткани, код и описание цвета, код и описание принта, ширина/вариант, базовая единица, активность. Временно допускается ключ полного названия + характеристики со статусом provisional.

Не объединять разные ткани по одному «С1». Не объединять близкие цвета, разную ширину или состав. Предлагаемые исправления опечаток — отдельные соответствия.

## 5. Условия поставщика `supplier_rule`

Поля: поставщик, материал/утверждённая группа материалов, цвет/принт, `lot_size`, `lot_unit`, `multiple_required=true`, `meters_per_kg` при необходимости, срок действия, источник подтверждения.

Правило вида ткани разворачивается только на утверждённые материалы этой группы. Если применимы два разных правила, расчёт заказа блокируется. Размер партии > 0, коэффициент > 0. Отсутствующий коэффициент и неприменимый коэффициент различаются.

## 6. Запасы `stock_snapshot`

Поля: дата/время снимка, склад, владелец, материал, партия, физическое количество, единица, заблокировано, брак, резерв, идентификатор назначения резерва. Доступное количество вычисляется по одной согласованной политике.

Нельзя складывать снимки разных дат как движения. Нельзя считать резерв и расход дважды. Ранее выданная в цех ткань не должна оставаться в доступном складском количестве.

## 7. Поставки `purchase_line` и `receipt_event`

Обязательные поля: ID заказа и строки/партии, материал, исходное количество, получено, отменено, остаток, единица, статус, дата готовности, отправки и ожидаемого/фактического прихода. Частичные поставки имеют собственные события.

Остаток = заказано − получено − отменено. Отрицательный остаток — ошибка. Переход production → transit → received не добавляет новую партию. Не объединять плановый приход и фактический как два поступления.

## 8. Потребление `material_demand_event`

Поля: ID задания, изделие, материал, дата потребления, количество, составляющая (base/defect/extra), связь с периодом продаж, состояние обеспечения и связь с резервом/выдачей. ID позволяет исключить повторный расход.

Спрос до горизонта и внутри горизонта может использовать одну модель событий. Граница определяется датой потребления, а не названием отчётного периода.

## 9. Результат `calculation_run`

Поля: ID запуска, время, версии кода/правил/связей, отпечатки входов, сценарий сроков, периоды, статус, число и объём нерешённых изделий, проблемы, строки потребности и заказа.

Проблема: код, серьёзность, затронутые записи, причина, требуемое действие. Примеры кодов: MISSING_BOM, AMBIGUOUS_MAPPING, DUPLICATE_COMPONENT, UNKNOWN_UNIT, MISSING_LOT, MISSING_CONVERSION, LATE_RECEIPT, STALE_SNAPSHOT.

Поля отчёта: `base_m`, `defect_m`, `extra_m`, `total_m`, доступное обеспечение, дефицит, партия, заказ м/кг, излишек, остаток, даты, полнота, источник. Неполный численный итог сопровождается количеством и объёмом исключённого спроса. Полностью невычислимое значение — null/«Нет данных», не 0.
